Where else did I paste that key?

After a leak the advice is always “revoke it and replace it everywhere.” keyroll is the everywhere: it maps every copy of your AI provider keys on this machine, asks each issuer which still work, and rotates one key in every file at once.

01
Why

    
“Revoke and replace those keys.” Replace them where, exactly?

    
On 2026-10-17 OpenCode said its Console had been breached and that third-party provider keys saved in a workspace may have been exposed. Their post passed a million views; people reported charges on keys they had forgotten about. Anthropic’s Lydia Hallie said they had revoked the Claude API keys they believe were affected, so some agents started failing with 401s overnight. And after rotating by hand, agents broke with “this API key has expired”, because the old key was still configured somewhere else.

    

      
Who was actually affected. OpenCode says it was 1.4% of OpenCode Console users, the subset who had linked external providers, and that everyone affected got an email. Keys you typed into the local OpenCode client reportedly never reached their servers (co-founder Dax, as relayed here; secondhand).

      
Either way, you can’t revoke what you can’t find: keyroll shows where each key sits, keyroll check tells you whether the issuer already revoked it, and keyroll rotate replaces it everywhere. If you ever pasted a key into an agent chat, it is also in the session transcripts; spillscan finds those.

    

    
One person audited their Mac and reported 1 token in 7 copies, two of them made by Claude Code’s automatic backups. That hunt is what keyroll does, in under a second, without sending anything anywhere.

  


  

    
02
Map · offline

    
Every copy, grouped by key, never printed.

    
keyroll reads the places agent tools keep keys (the full list), your shell rc files and history, and the .env files in your projects. It shows each key as issuer, the first characters and the last four (sk-ant-…M1AA), and a fingerprint, the first 8 hex characters of its SHA-256. The key itself never appears in output, JSON or MCP.

    

      
live
A tool reads it. rotate writes the new key here.

      
leftover
Nothing reads it, but it still unlocks your account: Claude Code backups, OpenCode’s pre-v2 auth.json, shell history, .env.example. rotate scrubs it and does not add the new key, so rotation shrinks the number of copies.

      
database
OpenCode v2 keeps keys in SQLite. keyroll never edits a database; it prints the exact command, like opencode auth login anthropic.

      
credential store
Claude Code, Codex, Gemini CLI, Goose and Zed can keep a key in the macOS Keychain, Windows Credential Manager or Linux Secret Service. keyroll asks whether those entries exist, by name, never reads a value, and lists each one as a by-hand step. Which names.

    

    
$ keyroll
  ● Anthropic   sk-ant-…M1AA  #38bb1575  9 copies  3 live · 1 database · 5 leftovers

03
Check · one free GET per key

    
Ask the issuer, not a guess.

    
keyroll check sends each key to its own issuer only, in a header, to an endpoint that costs nothing: a model list or the key-info route. Redirects are not followed, so the header cannot travel to another host. OpenRouter also tells us whether the key has a spend limit, and keyroll says so when it doesn’t. swipe the table →

    
REJECTED means the issuer refuses the key: revoked, deleted or mistyped (they answer all three the same way, so keyroll claims no more). If Claude Code started failing with 401 tonight, this is the line that tells you it is the issuer, not your code. A 402 or an out-of-credit 429 means the key works; a bare 429, any other 403 or a 5xx is unknown, never rejected. Exit code 1 means a rejected key is still configured somewhere.

  


  

    
04
Rotate · paste once

    
Every live copy rewritten, byte for byte. Everything else left alone.

    
    
      
  • The new key is read from a hidden prompt or stdin, never from an argument (shell history), and keyroll asks the issuer whether it works before writing it. Pasting an OpenAI key where an Anthropic one belongs is refused.
    • 
      
  • Only the old key’s bytes are replaced. Comments, key order, indentation and every other key in the file stay as they were, so .claude.json stays valid JSON and your .zshrc diff is one line.
    • 
      
  • Each file is written atomically: temp file in the same folder, original permissions (600 stays 600), fsync, rename. Symlinks are written through to their target. If a file changes while keyroll is rewriting it, that file is left untouched.
    • 
      
  • Originals go to ~/.keyroll/backups/ (folder 700, files 600) and show up in the next map as leftovers, so you can delete them once the old key is revoked.
    • 
      
  • A credential-store entry that may hold the key (say Claude Code’s "Claude Code" Keychain item) is listed with that tool’s own re-login step. keyroll cannot see whether it holds the old key, so it never touches it and does not count it as a copy.
    • 
      
  • Afterwards keyroll scans again and tells you how many places still hold the old key, then the revoke and spend-limit links for that issuer.
    • 
      
  • With --ci owner/name, the repo’s GitHub Actions secrets whose names point at the same issuer join the plan as by-hand steps, each with its gh secret set line (below).
    • 
      
  • The last line is always the old key’s status. keyroll asks the issuer one more time: now REFUSES it, revoked, or still ACCEPTS it, NOT revoked yet, because a copy keyroll cannot see (a hosted console, a CI secret, another machine) can still spend on it until you click revoke.
    • 
    

    
$ keyroll rotate 38bb1575 --dry-run

  


  

    
05
CI · names only

    
The copy that is not on your disk.

    
A key you rotated on your laptop can still sit in a repo’s Actions secrets, and the next workflow run fails with the same 401. keyroll ci asks GitHub, through the gh you are already logged in with, which repository, environment and organization secret names look like provider keys: ANTHROPIC_API_KEY, an org’s PROD_ANTHROPIC_KEY, CLAUDE_CODE_OAUTH_TOKEN (a login token, kept apart). GitHub never returns secret values to anyone, so keyroll never sees one. Each match comes with its exact replacement step, and keyroll rotate <fp> --ci owner/name adds them to the plan.

    
$ keyroll ci --all
keyroll ci  7 of 11 secret names in 2 repos look like AI provider keys · names only

  octo-demo/agent-bot
      repository     ANTHROPIC_API_KEY        Anthropic API key · updated 2026-10-03
                     → gh secret set ANTHROPIC_API_KEY --repo octo-demo/agent-bot

  


  

    
06
Never

    
What it will not do.

    
    
      
  • Print a key, put one in JSON, or hand one to an agent over MCP.
    • 
      
  • Read a value from your Keychain, Credential Manager or Secret Service. It asks whether an entry with a known name exists, and that is all (--no-credstore skips even that).
    • 
      
  • Send anything during keyroll (map). check contacts only each key’s own issuer.
    • 
      
  • Edit a database, a keychain, or a file it cannot write back atomically.
    • 
      
  • Set or read a CI secret. keyroll ci lists names through read-only gh calls and prints the gh secret set line for you to run.
    • 
      
  • Store keys. It is not a secret manager; it helps you get to one.
    • 
      
  • Read agent chat transcripts. Keys pasted into chats are spillscan’s job.
    • 
    

  


  

    
07
For agents · MCP

    
Let your agent ask “where is this key?”, read-only.

    
keyroll mcp is a stdio MCP server with two read-only tools: key_map (keys, fingerprints, copy counts) and key_copies (every file holding one key, plus credential-store entries by name). Neither returns key material, and there is no tool that writes; rotating stays a human step.

    
claude mcp add keyroll -- keyroll mcp
